1. 先做资源预算，再比较图计算框架

“有一百万节点”还不足以决定算法能否在单机运行。关键还有边数 m、边权类型、有向性、平均度与最大度、重复事件数、内存布局、查询类型及 SLA。例如 n=1,000,000 的稠密 n×n float64 邻接矩阵约需 8×10¹² 字节，也就是 8 TB（十进制）。然而如果这是 m=5,000,000 条无向边的简单图，按每条边存两份稀疏条目，一种使用 int64 索引和 float64 值的 CSR 概念存储仅约 168 MB，不包括元数据与容器开销。相差两个数量级以上的原因，是表示方式而非“选择了某家框架”。

精确计算：CSR 使用长度 n+1 的 indptr，长度 nnz 的 indices 和 data。若无向边不含自环与多重边，存储双向邻接时 nnz≈2m；假设三数组都按 8 字节存储，约为 8(n+1)+16m+16m=8(n+1)+32m 字节。若后端支持 int32 index 或 bool/float32 data，字节数又会不同。Python 字典、节点标签映射、属性对象、内存分配器以及实际算法工作区都没有计入这 168 MB，绝不能称为 NetworkX 内存实测。

MCSR≈8(n+1)+16·2m,Mdense=8n2

2. 图算法复杂度必须带上对象与实现条件

对邻接表表示的无权图，BFS/DFS 从一个起点遍历可达部分的时间上界 O(n+m)，适合连通性和无权最短路。若要从每个节点运行 BFS 求精确全对最短路，最坏时间上界会增加到 O(n(n+m))，不能说“BFS 是线性，所以精确全对距离也线性”。Brandes 算法计算全部节点的无权介数中心性，常见时间复杂度是 O(nm)，加权图中可涉及优先队列及更高成本；具体内存需求还受实现和图类别影响。

问题常见理论上界隐藏的条件/边界
单源 BFS/DFSO(n+m)邻接表、可达部分、无权
所有节点对无权最短路O(n(n+m))（重复 BFS）不要和单次 BFS 混淆
无权介数（Brandes）O(nm)需要保存依赖与路径数量
多轮 PageRankO(k(n+m))（稀疏迭代）迭代次数 k、容差与 dangling 处理
力导向可视化与迭代及力模型相关通常不能从边数直接推断运行时间
Neo4j 多跳匹配依查询计划和路径数量不是简单 O(m) 的统一承诺

这些是算法层面的渐近表达，不是某家库的绝对性能保证。性能测量还需包括输入解析、索引构建、物理内存峰值、冷/热缓存、图副本数和输出序列化时间；只计一个函数调用可能把大部分实际成本隐藏起来。

3. 大图采样：随机选点与随机游走看到的不是同一群人

Uniform Node Sampling（均匀采样节点）让每个原图节点在抽样时有相同入样机会，抽样后通常使用诱导子图；但在稀疏图中会丢失大量边并改变连通性。随机游走取样在无向连通图上，基本随机游走的稳态概率正比于度：π(v)=d(v)/(2m)，更容易遇见高连接节点。随机游走样本的高平均度不一定代表原图就有那么多高连接用户，尤其短链、未混合和分量边界会增加偏差。

π(v)=d(v)2m

对 K₁,₅ 星形网络，中心节点度为 5，五个叶子度均为 1，边数 m=5；随机游走的长程访问比例中心为 5/(2×5)=1/2，而均匀节点抽样中心概率只有 1/6。即使整个网络没有任何“更有名”的社会含义，采样机制本身也会让中心更常被观察。星形图是二部周期图，随机游走在时间奇偶上会振荡；上述稳态概率可以通过长期占据比例、懒惰随机游走或适当平稳初始分布解释，不能不检查混合就宣称每个有限步的分布都等于 π。

稳态是理论长期占比，不是一次有限步抽样结果。

Leskovec 与 Faloutsos（KDD 2006）研究了不同图采样方法对结构统计的影响。采样评估不能只检查样本节点数：还需比较度分布、分量规模、聚集系数、路径分布、社团结构与任务目标。有时对全局性质均匀节点采样表现良好；对传播路径或稀有桥梁则可能特别糟糕。不存在适用于所有图和指标的万能采样法。

4. NetworkX、igraph、稀疏矩阵与图数据库的选择

NetworkX 强调 Python 友好、属性灵活和算法丰富，适合探索式分析与小中型图；其 Python 对象与字典存储可能增加内存和遍历开销。igraph 核心图存储与多种算法采用更紧凑的原生实现，在许多图算法上具备效率优势，但速度优势依工作负载、节点/属性类型和数据传输成本而不同。SciPy 的 CSR/CSC 更适合线性代数、稀疏传播与矩阵运算，但不自动替代所有图查询与属性建模。

Neo4j 的图数据库适合属性图、持久化、约束、权限与关系模式查询。Cypher 的 MATCH 能描述节点—关系模式；索引可帮助找到起始节点，而后续多跳扩展的代价仍依图的分支因子与匹配结果。必须使用 EXPLAIN 审查计划、必要时用 PROFILE 测真实执行，而不能仅凭“用了图数据库”就认定任何最短路径和全图统计自动更快。

# Neo4j Cypher：运行于你自己的数据库，且事先创建 Person 标签与 KNOWS 关系
CREATE INDEX person_id IF NOT EXISTS FOR (p:Person) ON (p.id);
EXPLAIN MATCH (p:Person {id: $person_id})-[:KNOWS]-(friend:Person)
RETURN friend.id LIMIT 20;
# PROFILE 会实际执行并分析统计；EXPLAIN 仅生成计划。

5. 为什么分布式并不是大图的第一反应

把图拆到多台机器会引入跨分区边通信、网络同步、重复状态、任务调度和容错开销。枢纽节点连接很多分区时尤其容易形成热点。图任务是否可并行，取决于算法是否主要局部遍历、是否多次全局同步、是否涉及优先队列或迭代收敛。先用流式读入、压缩索引、外存算法、单机并行与近似统计，评估是否已满足 SLA，再决定是否跨机器扩展。

“千万节点以内 igraph 毫无压力”这样的经验描述没有确定的边数、设备、图结构和算法，不能当技术保证。现代工具也会不断更新，正式技术选型应冻结版本、使用相同图数据、固定机器、测多次 warm-up 后分布和峰值 RSS，并将图导入时间包含在端到端成本中。

6. 使用标准库手算 CSR 与采样偏差

以下可执行示例不创建百万节点图，只计算给定 n/m 的存储字节与星形图理论概率，断言本章关键数字，避免把“公式结果”误报成性能测试。

from math import isclose

def memory_bytes(n, m):
    if n < 2 or m < 0 or m > n * (n - 1) // 2:
        raise ValueError("undirected simple graph contract")
    dense = 8 * n * n
    csr = 8 * (n + 1) + 16 * (2 * m)
    return dense, csr

def star_center_probs(leaves):
    if leaves < 1:
        raise ValueError("nonempty star required")
    uniform = 1 / (leaves + 1)
    random_walk_stationary = leaves / (2 * leaves)
    return uniform, random_walk_stationary

dense, csr = memory_bytes(1_000_000, 5_000_000)
assert dense == 8_000_000_000_000
assert csr == 168_000_008
uniform, walk = star_center_probs(5)
assert isclose(uniform, 1 / 6)
assert isclose(walk, .5)
print("theoretical bytes:", dense, csr)

实际框架基准应在相同数据、缓存状态和硬件条件下单独执行。本文不报告任何未经实测的 NetworkX/igraph/Neo4j/GraphX 倍速排序，也不假定某些云服务一定具有更低总成本。

7. 从目标出发的一套工程决策顺序

先定义图与业务问题 → 计算 n、m、属性/边权和理论内存预算 → 选择正确且可测的算法 → 验证结果不变量 → 只在资源瓶颈真实存在时升级到稀疏、原生库、数据库或分布式系统。对于采样与近似算法，还要报告统计偏差、置信区间和失败案例。工具选型不是品牌排名；它是有证据支持的工作负载匹配。
